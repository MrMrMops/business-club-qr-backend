# Business Club QR Backend

Backend-сервис для регистрации гостей мероприятия, выдачи персональных QR-пропусков и начисления баллов при check-in.

Проект реализован в рамках тестового задания на позицию Backend-стажёра.

## Возможности

Проект включает:

- FastAPI API;
- Telegram-бот на aiogram;
- PostgreSQL;
- SQLAlchemy;
- Alembic migrations;
- персональные HMAC-подписанные QR-пропуска;
- распознавание QR-кодов с фотографий через OpenCV;
- историю начисления баллов;
- защиту от повторного check-in;
- защиту от конкурентного двойного начисления;
- Docker / Docker Compose;
- автоматические тесты;
- production deployment в Railway.

---

## Основной сценарий

### Гость

Гость регистрируется в системе и получает:

- имя;
- категорию;
- Telegram ID;
- персональный `pass_id`;
- баланс баллов.

В Telegram-боте гость может использовать:

```text
/qr
```

Бот отправляет персональный QR-пропуск картинкой.

Также доступна команда:

```text
/balance
```

Она показывает текущий баланс гостя.

---

### Организатор

Организаторы определяются через allowlist Telegram ID:

```env
ORGANIZER_TELEGRAM_IDS=[123456789,987654321]
```

Организатор может сфотографировать QR-код гостя или переслать его изображение Telegram-боту.

Бот:

1. распознаёт QR через OpenCV;
2. проверяет HMAC-подпись;
3. находит гостя;
4. показывает карточку гостя;
5. показывает имя и категорию;
6. показывает текущий баланс;
7. показывает статус check-in;
8. позволяет отметить приход и начислить баллы кнопкой.

Также доступен ручной fallback:

```text
/check TOKEN
```

Он нужен на случай, если QR-код не удалось распознать с фотографии.

Команда:

```text
/id
```

показывает Telegram ID пользователя. Это удобно для добавления организаторов в allowlist.

---

## Check-in

При первом check-in:

- устанавливается `checked_in_at`;
- гостю начисляются баллы;
- создаётся запись в истории начислений.

Повторный check-in не начисляет баллы ещё раз.

Начисление реализовано атомарной операцией в PostgreSQL:

```text
UPDATE users
WHERE checked_in_at IS NULL
```

Поэтому защита работает не только при последовательном повторном сканировании, но и если два организатора одновременно пытаются отметить одного и того же гостя.

Только одна операция сможет изменить запись и начислить баллы.

Количество баллов за check-in задаётся переменной окружения:

```env
CHECKIN_POINTS=100
```

---

## История начислений

Текущий баланс хранится у гостя в поле:

```text
points
```

При этом каждое начисление дополнительно записывается в таблицу:

```text
point_transactions
```

Для каждой операции сохраняются:

- кому начислили баллы;
- Telegram ID организатора;
- количество баллов;
- причина начисления;
- время начисления.

Для check-in используется причина:

```text
event_checkin
```

Таким образом, система хранит не только текущий баланс, но и историю начислений.

---

## Безопасность QR-пропуска

QR-код не содержит обычный ID гостя.

Для каждого гостя при регистрации генерируется случайный:

```text
pass_id
```

На его основе формируется токен:

```text
pass_id.HMAC_SIGNATURE
```

Подпись создаётся с помощью:

```text
HMAC-SHA256
```

и секрета:

```env
PASS_TOKEN_SECRET=...
```

При чтении QR подпись проверяется безопасным сравнением.

Если изменить `pass_id` или подпись вручную, такой пропуск не пройдёт валидацию.

---

## Распознавание QR по фотографии

Основной сценарий для организатора — отправить Telegram-боту фотографию QR-кода.

Изображение декодируется через:

```text
OpenCV QRCodeDetector
```

После распознавания полученный токен проходит обычную HMAC-валидацию.

Если распознать изображение не удалось, остаётся ручной fallback:

```text
/check TOKEN
```

## Архитектура

Проект разделён на несколько слоёв.

### `app/api`

HTTP API на FastAPI.

Используется, в частности, для регистрации гостей.

### `app/bot`

Telegram-бот и обработчики:

- `/qr`;
- `/balance`;
- `/check`;
- `/id`;
- фотографий QR-кодов;
- inline-кнопки check-in.

### `app/services`

Ключевая бизнес-логика приложения:

- создание и поиск гостей;
- создание и проверка HMAC-токена;
- check-in;
- определение организаторов;
- генерация QR;
- декодирование QR с изображения.

Критичная бизнес-логика не завязана напрямую на Telegram handlers и может тестироваться отдельно.

### `app/db`

SQLAlchemy-модели и подключение к PostgreSQL.

### `alembic`

Версионирование схемы базы данных.

### `tests`

Тесты основной бизнес-логики и FastAPI endpoints.

Хранит:

- `id`;
- `telegram_id`;

- имя;
- категорию;
- случайный `pass_id`;

## Принятые решения

### Почему используется случайный `pass_id`

В QR не используется Telegram ID или ID записи пользователя.

Вместо этого генерируется отдельный случайный идентификатор пропуска.

Даже знание ID другого гостя не позволяет построить его QR.

---

### Почему используется HMAC

Для задачи не требуется хранить отдельную сессию или авторизацию для каждого QR.

HMAC позволяет:

- подписать токен;
- проверить его подлинность;
- обнаружить изменение содержимого;
- не хранить подпись отдельно в базе.

---

### Почему баланс и история хранятся одновременно

Поле:

```text
users.points
```

позволяет быстро получить текущий баланс.

Таблица:

```text
point_transactions
```

позволяет восстановить историю начислений и определить, кто, когда, сколько и за что начислил.

---

### Почему `checked_in_at` хранится у гостя

В рамках тестового задания реализуется одно мероприятие.

Поэтому отдельная сущность посещения мероприятия была бы избыточной.

Поле:

```text
checked_in_at
```

достаточно для определения, был ли уже выполнен check-in.

При расширении системы на несколько мероприятий текущий баланс пользователя и персональный QR можно сохранить без изменений.

Следующим шагом будет добавление сущностей:

```text
events
event_checkins
```

Например:

```text
events
------
id
name
starts_at
location
checkin_points

event_checkins
--------------
id
user_id
event_id
organizer_telegram_id
checked_in_at
```

С ограничением:

```text
UNIQUE(user_id, event_id)
```

В таком варианте у гостя останется один постоянный персональный QR для всех мероприятий, а повторный check-in будет запрещён только внутри конкретного мероприятия.

Накопленные баллы при этом продолжат храниться в `users.points`, а история всех начислений — в `point_transactions`.

---

### Почему check-in реализован атомарно

Простой сценарий:

1. прочитать `checked_in_at`;
2. проверить, что он пустой;
3. начислить баллы;

может привести к race condition.

Поэтому используется условный SQL `UPDATE`.

Только одна конкурентная операция может успешно выполнить check-in.

История начисления создаётся в той же транзакции.

---

### Почему используется OpenCV

Ручной ввод токена неудобен при регистрации большого количества гостей.

OpenCV позволяет автоматически распознать QR непосредственно с фотографии, отправленной организатором в Telegram.

Ручная команда `/check TOKEN` оставлена только как fallback.

# Запуск

## 1. Клонировать репозиторий

```bash
git clone https://github.com/MrMrMops/business-club-qr-backend.git
cd business-club-qr-backend
```

---

## 2. Создать `.env`

```bash
cp .env.example .env
```

Заполнить переменные:

```env
DATABASE_URL=postgresql+asyncpg://business_user:business_password@localhost:5432/business_club

TELEGRAM_BOT_TOKEN=your_bot_token
TELEGRAM_BOT_USERNAME=your_bot_username

PASS_TOKEN_SECRET=your_secret_key

ORGANIZER_TELEGRAM_IDS=[123456789]
CHECKIN_POINTS=100
```

Для нескольких организаторов:

```env
ORGANIZER_TELEGRAM_IDS=[123456789,987654321]
```

Для генерации секрета можно использовать:

```bash
python -c "import secrets; print(secrets.token_urlsafe(32))"
```

---

## 3. Запустить проект

Проект запускается одной командой:

```bash
docker compose up -d --build
```

Docker Compose:

1. запускает PostgreSQL;
2. ждёт готовности базы данных;
3. выполняет Alembic migrations;
4. запускает FastAPI;
5. запускает Telegram-бота.

Проверить состояние:

```bash
docker compose ps
```

Остановить проект:

```bash
docker compose down
```

```text
http://localhost:8000/docs
```

```http
POST /guests
```

```json
{
  "name": "Test Guest",
  "category": "guest",
  "telegram_id": 123456789,
  "username": "test_user"
```

Пример ответа:

```json
{

  "username": "test_user",

```

```text

```

```text
422 Unprocessable Entity
```

## Пример решения, которое было изменено

На раннем этапе рассматривался сценарий, в котором QR фактически являлся одноразовым кодом на получение баллов и использовался самим гостем.

После повторного анализа задания от этого решения я отказался, потому что оно не соответствовало требуемому сценарию.

Финальная архитектура устроена иначе:

```text
гость
→ получает постоянный персональный QR

организатор
→ сканирует QR
→ получает карточку гостя
→ нажимает кнопку check-in
→ баллы начисляются один раз
```

Таким образом QR является именно персональным пропуском гостя, а не одноразовым купоном на баллы.

Также отдельно была пересмотрена реализация повторного check-in.

Вместо обычной проверки значения в Python используется атомарная операция в PostgreSQL. Это защищает систему от конкурентного двойного начисления.

Во время финального code review также было найдено и удалено дублирование Telegram callback-handler.
